# Business flow — search → predict → click, mapped to the three agents (2026-09-20)

The end-to-end product flow, written against the **code that exists today** (the
`divcore` audit in `2026-09-20-two-agent-split.md`), not an aspiration. Companion to
that doc: it defines *what runs when*; this defines *the user journey and the data
that moves through it*. Agent shapes (Graph/Swarm) and the deferred Agent-1 promote
live there — here we trace the flow.

## Surfaces

| Surface | Role |
|---|---|
| **divreact** (frontend) | search bar, calendar list, per-row detail panel; fetches Yahoo facts client-side |
| **divcore** (FastAPI) | the agents: predict+publish, analyze; forward-rate; reconcile |
| **Yahoo** | quote + dividend history (client), forward-rate refresh (server fallback) |
| **Signal providers** | FMP, Finnhub, Alpha Vantage, Tavily, Yahoo-news RSS, dividendhistory.org |
| **divmcp** | `web_search` + `fetch_url` (Agent 2's open-ended reach, post-migration) |
| **Google Calendar** | the published schedule + the forward-rate cache (event private props) |

## The three agents (one line each)

- **Agent 0 — predict + publish.** Facts → pattern (deterministic) → research (1 LLM
  call) → forward yield (deterministic) → calendar upsert → reconcile.
- **Agent 1 — resolve declared.** Pin the real announced amount/dates. Today a shared
  3-tier substrate inside `gather_dividend_signals`; consumed by 0 and 2.
- **Agent 2 — analyze one row.** Open-ended read (news/forums/rumor) around the fixed
  declared number. Single LLM call today; Swarm after migration.

## Flow 1 — Search a ticker

```
user types ticker ─▶ divreact fetches Yahoo (quote + dividend history)
                     ─▶ builds `facts`: price, currency, pastYearDividends[],
                        ttmAmount, forward/trailing yield, companyName,
                        nextExDate/nextAmount (Yahoo's scheduled next ex-date)
                     ─▶ renders the ticker's known dividends
```

- **No agent, no backend.** Client-side only (matches divreact's "client-side Yahoo
  facts"). ~2 Yahoo calls: quote/price + dividend history.
- These `facts` are **authoritative** — everything downstream echoes them verbatim
  and never re-derives them.

## Flow 2 — Predict button (Agent 0)

One call to `predict_and_publish(req)`; `req.facts` are the search's authoritative facts.

```
facts (verbatim, layer 1)
   ▼
age_pattern            ← layer 2, DETERMINISTIC: cadence, specials, gap/cut, projection
   ▼
research_prediction    ← layer 3, ONE LLM call over facts+pattern+grounding+signals
   │                      declared-check first; degrades to pattern, never dropped
   │   └── internally: gather_dividend_signals → resolves declared (Agent 1 substrate)
   ├────────▶ forward rate  ← DETERMINISTIC (ser_forward_rate), priced at latest price
   ▼
_plan_events           ← one item per ex-date; rank scheduled < confirmed < estimate < prediction
   ▼
publish → GCal upsert ─▶ reconcile_declared  ← declared fact overwrites the prediction row
```

Rules that hold here (all already implemented — preserve them):

- **Calendar is written; Postgres is not.** `div_cal_trade` rows appear only when the
  user later adds a tick on the Trades tab. Predict never writes the DB.
- **`publishToCalendar=false` = preview** — computes all three layers, writes nothing.
- **`divstatus` is only `Declared | Prediction`.** (Renamed from `Confirmed`;
  `gcal_api` normalizes legacy `"Confirmed"` on read and migration `b3c7d8e9f0a1`
  rewrites DB rows.) The scheduled/confirmed/estimate/prediction *rank* is
  date-collision precedence, not a public status.
- **Never dead-ends.** LLM/parse failure → the pattern's next projection as a
  LOW-confidence prediction, sourced by what was gathered. And when both the
  pattern and research layers withhold (variable payers), `_plan_events` still
  writes Yahoo's `nextExDate`/`nextAmount` as a `_RANK_SCHEDULED` (-1) anchor,
  stamped confidence `0.01` (renders "1%") — the date is dependable, the
  forward-rate amount is not — so the row gets a forward calendar entry instead
  of nothing. A real estimate/prediction on the same date still outranks it.
- **Forward rate is cached + lazily refreshed** in the GCal event props
  (`enrich_forward_rates`): first viewer of the day recomputes stale symbols; freshly
  predicted symbols are already stamped `priceAsOf = today` and skip the fetch.
- **Grounding facts are stamped on the event** (`_profile_props`): `companyName`,
  `currency`, `ttmAmount`, and `pastYearDividends[]` (JSON) are written to each
  event's private props at publish, so the calendar — not a re-fetch — is the store
  for the facts the click/analyze path reuses. `reconcile_declared` carries them
  over onto the declared row.

Result: the ticker's dividend schedule (past confirmed + projected/predicted future)
is on the public calendar, forward yield stamped, declared rows reconciled to fact.

## Flow 3 — Click a row (detail panel)

The list shown = published calendar rows. Clicking one opens the analysis panel.

```
click row
   │
   ├─ divstatus == Declared / already declared ──▶ Agent 2 (analyze around the fact)
   │
   └─ not declared (Prediction) ──▶ Agent 1 (resolve declared) ──▶ Agent 2
                                    │
                                    └─ TODAY this is implicit: analyze_dividend calls
                                       gather_dividend_signals, which resolves declared
                                       first (FMP → dividendhistory.org → LLM extract),
                                       then the analysis LLM reasons over it.
```

Agent 2 (`analyze_dividend`) today:

- **Two layers in one LLM call:** FACT check (does a declared amount override this
  stale row?) then LEADING read (payout coverage, FCF, yield, analyst notes, forum
  chatter → risk before the board announces).
- **Reconciles concurrently:** if signals show a declaration, `reconcile_declared`
  fires alongside the analysis call and silently corrects the row.
- **Never surfaces an error box** — degrades to a low-signal read.
- **Grounded, never invents:** cites only URLs present in the gathered signals.
- **Reuses the row's stored facts, no re-fetch:** the grounding `facts` sent to the
  analyze call are read off the clicked calendar row (`factsFromItem`), which carries
  the facts stamped at Predict time; `trailingYield` is derived from `ttmAmount/price`.
  A live Yahoo fetch (`loadFacts`) happens only as a fallback for rows published
  before facts were persisted. So by click time the grounding input is already
  certain — collected once at query/Predict, not re-derived per click.

Post-migration this single call becomes the **Swarm** (news scout ⇄ forum/sentiment
digger ⇄ skeptic ⇄ synthesizer), still handed the resolved declared number as
immutable ground truth.

Scope note: Agent 1 resolves **the clicked row's / searched ticker's** number — not a
batch resolve of the whole list. Declared rows skip Agent 1 at zero LLM cost.

## Trigger map (the whole flow at a glance)

| UI action | Runs | Writes | LLM? |
|---|---|---|---|
| Search a ticker | Yahoo fetch (client) | — | no |
| Predict button | Agent 0 (+ Agent 1 inside) | Google Calendar | 1 call (research) |
| Click row — declared | Agent 2 | reconcile (if drift) | 1 call (analyze) |
| Click row — not declared | Agent 1 → Agent 2 | reconcile (if declared) | resolve + analyze |
| Add tick (Trades tab) | — | Postgres `div_cal_trade` | no |

## Ground-truth invariant (spans all flows)

The **declared number is a deterministic fact**, produced once by Agent 1's resolver
and *consumed* by everyone else: Agent 0 uses it as a high-confidence `predictedNext`,
Agent 2 reads risk *around* it, `reconcile_declared` writes it over stale rows. No
agent — not even the open analyze swarm — invents or overwrites it. The LLM's job is
the *leading read*, never the number.
